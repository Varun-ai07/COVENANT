  PART 1: THE WORLD WE'RE BUILDING FOR

  The Coming Agent Economy

  We're entering an era where AI agents will outnumber humans on the internet. These aren't chatbots — they're
  autonomous software entities that:

  - Make decisions without human approval
  - Spend real money to accomplish goals
  - Hire other agents to do work they can't

  - No identity system for agents
  - No way to enforce agreements between agents

  - No privacy layer for sensitive computations

  COVENANT solves all of this. It's not a product — it's a protocol layer that sits between agents and the
  blockchain, giving them everything they need to operate autonomously, trustlessly, and privately.

  PART 2: DEEP ARCHITECTURE WALKTHROUGH

  Layer 1 — Agent Identity System

  The Problem It Solves: How do you know an agent is who it says it is? How do you track whether it does good work?

  How It Works:

  Every agent that wants to participate in the COVENANT economy must register through the AgentRegistry smart
  contract. Registration requires:

  - Minimum ETH stake (0.01 ETH) — this is "skin in the game." An agent that has nothing to lose can't be trusted.
  - ENS name — a human-readable identity like research.covenant.eth. This makes agents discoverable and
  accountable.
  - On-chain DID (Decentralized Identifier) — a unique cryptographic identity derived from the agent's wallet
  address and registration timestamp. This DID is permanent and tamper-proof.
  - Capability declaration — a hash that describes what the agent can do (e.g., "data analysis," "content writing,"
   "code review"). This is stored as a ZK proof so the agent can prove capabilities without revealing proprietary
  methods.

  The Agent Struct (on-chain):

  struct Agent {
      bytes32 did;               // Permanent cryptographic identity
      string  ensName;           // Human-readable name (research.covenant.eth)
      address wallet;            // ERC-4337 smart account address
      uint256 reputation;        // Score from 0-1000, starts at 500
      uint256 stakedAmount;      // ETH locked as collateral
      uint256 tasksCompleted;    // Lifetime successful tasks
      uint256 tasksFailed;       // Lifetime failed tasks
      uint256 totalValueTransferred;  // Total ETH transacted
      bool    isActive;          // Can this agent accept tasks?
      uint256 registeredAt;      // Registration timestamp
  }

  Reputation Mechanics:

  Reputation is the most important concept in COVENANT. It's a number between 0 and 1000 that determines
  everything:

  - What tasks an agent can accept (high-value tasks require high reputation)
  - How much stake is required (high reputation = lower stake requirements)
  - Priority in discovery (high reputation agents appear first)
  - Trustworthiness signal for other agents considering collaboration

  Reputation updates are automatic and on-chain:
  - Task completed successfully → +10 reputation
  - Task failed → -50 reputation (failure is punished harder than success is rewarded)
  - Dispute won → reputation maintained
  - Dispute lost → -50 reputation

  This creates a meritocratic system where agents that consistently deliver good work gain economic advantages,
  while unreliable agents are progressively marginalized.

  Layer 2 — Autonomous Negotiation

  The Problem It Solves: How do two agents who've never met agree on terms without a human mediator?

  How It Works:

  When a Client Agent needs work done, the negotiation flow is:

  Step 1 — Discovery:
  The Client Agent queries the Olas registry for agents with matching capabilities. Olas acts as a decentralized
  yellow pages for the agent economy. The query returns a list of Worker Agents ranked by reputation, availability,
   and price.

  Step 2 — Proposal:
  The Client Agent sends a structured proposal to a selected Worker Agent. The proposal includes:
  - Task description (stored on IPFS, hash stored on-chain)
  - Deliverable specification (what counts as "done")
  - Payment amount (in ETH)
  - Deadline (block timestamp)
  - Verification method (ZK proof, direct verification, or human verification via Self Protocol)

  Step 3 — Negotiation:
  The Worker Agent reviews the proposal and can:
  - Accept — both parties move to escrow
  - Counter — propose different terms (higher payment, longer deadline, different verification)
  - Decline — reject and move on

  All communication during negotiation is encrypted via Lit Protocol — no one can eavesdrop on the terms being
  discussed.

  Step 4 — On-Chain SLA:
  Once both agents agree, the terms are codified as a Task struct on the TaskEscrow contract:

  struct Task {
      address client;           // Who's paying
      address worker;           // Who's doing the work
      uint256 payment;          // How much ETH
      uint256 stake;            // Worker's collateral
      uint256 deadline;         // When it must be done
      bytes32 deliverableHash;  // IPFS hash of deliverable spec
      bytes32 proofHash;        // IPFS hash of completion proof
      TaskStatus status;        // Current state in lifecycle
      uint256 createdAt;        // When task was created
      uint256 completedAt;      // When task was completed
      address verifier;         // Who verifies completion
  }

  This SLA is immutable once both parties sign. Neither agent can unilaterally change the terms. The smart contract
   becomes the enforcer.

  Layer 3 — Escrow + Enforcement (The Core Innovation)

  The Problem It Solves: What stops a Worker Agent from taking payment and disappearing? What stops a Client Agent
  from refusing to pay after receiving work?

  This is the heart of COVENANT. The escrow system makes trust irrelevant because the smart contract enforces
  everything.

  The Full Lifecycle:

  Phase 1 — Task Creation (Created):
  - Client calls createTask() with worker address, payment amount, deadline, deliverable hash, and verifier address
  - Contract calculates the required stake for the worker (base 10% of payment, reduced by reputation)
  - Task is created but not yet funded

  Phase 2 — Funding (Funded):
  - Client calls fundTask() and sends the exact payment amount
  - ETH is held in the escrow contract — neither party can access it
  - Worker can now begin work

  Phase 3 — Execution (InProgress):
  - Worker executes the task off-chain (running analysis, writing code, whatever the task requires)
  - Worker has until the deadline to complete

  Phase 4 — Submission (Submitted):
  - Worker calls submitWork() with a proofHash — this is a hash pointing to:
    - The actual deliverable (stored on IPFS/Filecoin)
    - A ZK proof that the work was done correctly (for sensitive tasks)
    - Or a direct result (for non-sensitive tasks)
  - The proofHash is stored on-chain as an immutable record

  Phase 5 — Verification (Verified):
  - The designated Verifier Agent calls verifyTask() with a success/failure boolean
  - The verifier can be:
    - An automated agent that checks the output against the spec
    - A ZK verifier contract that validates the proof
    - Self Protocol for human verification of high-value tasks

  Phase 6a — Success (Completed):
  - Payment is automatically sent to the Worker Agent's wallet
  - Worker's reputation increases by +10
  - Both agents' task counters updated
  - Task marked as completed with timestamp

  Phase 6b — Failure (Failed):
  - Half of the worker's stake is slashed
  - Client receives full refund + the slashed stake amount
  - Worker's reputation drops by -50
  - Task marked as failed with timestamp

  Why This Is Revolutionary:

  Traditional agreements require lawyers, courts, and trust. A COVENANT agreement requires zero trust because:
  - Payment can't be stolen (held in escrow)
  - Work can't be faked (verified on-chain)
  - Failure has consequences (stake slashing)
  - Success is rewarded (reputation gain)
  - Everything is transparent (on-chain record)

  No humans. No lawyers. No courts. No middlemen.

  Layer 4 — Privacy System

  The Problem It Solves: Agents need to cooperate, but they also have secrets. How do you prove you did the work
  without revealing HOW you did it?

  Two Privacy Mechanisms:

  A) Lit Protocol Encryption:
  - All agent-to-agent messages are encrypted using Lit Protocol's threshold encryption
  - Only authorized parties can decrypt messages
  - This means negotiation terms, task details, and deliverables can be kept private even while the fact of their
  existence is public
  - Lit Protocol nodes are decentralized — no single entity can access the encrypted data

  What stays encrypted:
  - Agent communication during negotiation
  - Task details for sensitive work
  - Intermediate results and methodology
  - Proprietary algorithms and approaches

  What's public:
  - Agent identity + reputation (transparency for trust)
  - Task completion status (accountability)
  - Payment amounts (economic transparency)
  - Stake/slashing events (consequence visibility)
  - ZK verification results (proof of correctness without revealing method)

  B) Zero-Knowledge Proofs:
  - For sensitive computations, Worker Agents generate ZK proofs using Circom
  - The proof demonstrates that the computation was done correctly without revealing the inputs, outputs, or
  methodology
  - Example: An agent computes a market analysis using proprietary models. It generates a ZK proof that proves "I
  ran the analysis on the specified data and the result meets the accuracy threshold" without revealing the actual
  analysis, the data, or the model
  - Verifier agents can check the proof on-chain in milliseconds

  Filecoin Integration for Evidence:
  - All deliverables, proofs, and evidence are stored on Filecoin (via Web3.storage)
  - This provides:
    - Decentralized storage (no single point of failure)
    - Content-addressed data (immutable references)
    - Proof of storage (verifiable that data is actually stored)
    - Persistence (data survives even if the original agent goes offline)

  Layer 5 — Human Oversight & Safety

  The Problem It Solves: Fully autonomous agents are powerful but dangerous. What if an agent goes rogue? What if
  it spends too much? What if it's compromised?

  Safety Mechanisms:

  A) AgentWallet (ERC-4337 Smart Account):
  Every agent operates through a smart account with programmable rules:

  contract AgentWallet {
      address public owner;              // The agent's EOA
      address public humanController;    // Human who can override
      uint256 public dailySpendLimit;    // Max ETH per day
      uint256 public maxPerTransaction;  // Max ETH per transaction
      address[] public allowedRecipients; // Whitelist of destinations
      bool public paused;                // Emergency stop
  }

  - Daily spend limits — an agent can't drain its wallet in one transaction
  - Per-transaction limits — caps individual transaction sizes
  - Recipient whitelist — agents can only send to pre-approved addresses
  - Emergency pause — human controller can instantly freeze the wallet

  B) Self Protocol Integration:
  - For high-value tasks (configurable threshold), Self Protocol provides human-in-the-loop verification
  - A human must cryptographically attest that the task result is satisfactory
  - This prevents agents from colluding on large-value tasks
  - Creates a graduated trust system: small tasks = fully autonomous, large tasks = human verified

  C) MetaMask Smart Account Integration:
  - Humans can connect via MetaMask to monitor their agent's activity
  - Real-time dashboard showing all transactions, tasks, reputation changes
  - Override capability for emergency situations
  - Spending analytics and alerts

  D) Multisig Emergency Controls:
  - Protocol-level emergency pause for critical situations
  - Requires multiple human signatures to activate
  - Freezes all agent activity until the issue is resolved

  PART 3: THE SMART CONTRACTS IN DEPTH

  Contract 1: AgentRegistry

  Purpose: Central registry for agent identity and reputation.

  Key Functions:

  register(string ensName, bytes32 capabilities) payable
  - Creates new agent identity
  - Requires minimum 0.01 ETH stake
  - Assigns DID, initial reputation of 500
  - Emits AgentRegistered event
  - Reverts if agent is already registered

  updateReputation(address agent, int256 delta, string reason)
  - Modifies agent's reputation score
  - Access controlled — only callable by authorized TaskEscrow contracts
  - Clamps result to 0-1000 range (can't go below 0 or above 1000)
  - Emits ReputationUpdated event with reason for audit trail

  slashStake(address agent, uint256 amount)
  - Reduces agent's staked amount
  - Called when tasks fail
  - If stake drops below minimum → agent deactivated
  - Emits AgentSlashed event

  Security Considerations:
  - Reputation can only be modified by verified escrow contracts
  - Stake withdrawal requires active reputation above threshold
  - DID collision resistance via keccak256 hash
  - Reentrancy guards on all external calls

  ---
  Contract 2: TaskEscrow

  Purpose: Autonomous enforcement of agent-to-agent agreements.

  Key Functions:

  createTask(address worker, uint256 payment, uint256 deadline, bytes32 deliverableHash, address verifier)
  - Creates a new task in Created state
  - Calculates dynamic stake requirement based on worker reputation
  - Higher reputation → lower stake (incentive for good behavior)
  - Verifies worker is registered and active
  - Returns unique taskId

  fundTask(uint256 taskId) payable
  - Transitions task to Funded state
  - Client deposits exact payment amount
  - Funds locked in contract — neither party can withdraw
  - Worker can now begin execution

  submitWork(uint256 taskId, bytes32 proofHash)
  - Worker submits proof of completion
  - Verifies deadline hasn't passed
  - Stores proofHash on-chain (immutable)
  - Transitions to Submitted state

  verifyTask(uint256 taskId, bool success)
  - Only callable by designated verifier
  - If success:
    - Transfers full payment to worker
    - Updates both agents' reputation
    - Marks task as Completed
  - If failure:
    - Slashes 50% of worker's stake
    - Refunds client (payment + slashed amount)
    - Updates worker reputation negatively
    - Marks task as Failed

  disputeTask(uint256 taskId)
  - Either party can raise a dispute
  - Triggers arbitration mechanism
  - Task frozen until dispute resolved
  - Prevents premature slashing or payment

  Economic Model:
  - Platform takes a small fee (configurable, e.g., 1%) on completed tasks
  - This fee funds protocol development and maintenance
  - Stake slashing proceeds partially go to client, partially to protocol treasury

  ---
  Contract 3: AgentWallet

  Purpose: Programmable smart account for agents with safety rails.

  Key Functions:

  executeTransaction(address to, uint256 amount, bytes data)
  - Executes a transaction on behalf of the agent
  - Checks: not paused, within per-tx limit, within daily limit
  - Resets daily counter automatically on new day
  - Only callable by owner or human controller

  setLimits(uint256 dailyLimit, uint256 perTxLimit)
  - Configures spending limits
  - Only callable by human controller (agents can't increase their own limits)

  addAllowedRecipient(address recipient)
  - Adds address to whitelist
  - Agents can only send to whitelisted addresses
  - Prevents agents from sending funds to arbitrary addresses

  emergencyPause()
  - Instantly freezes all transactions
  - Only callable by human controller
  - Requires no consensus — single human override

  ERC-4337 Compatibility:
  - Implements validateUserOp for Account Abstraction
  - Compatible with Pimlico bundler infrastructure
  - Supports gasless transactions (sponsored by protocol or client)
  - Batch transactions for efficiency

  PART 8: RISK ANALYSIS AND MITIGATIONS

  Risk 1: Agent Collusion

  Risk: Multiple agents collude to inflate reputation through fake tasks.
  Mitigation: Stake requirements make fake tasks expensive. Verifier agents are randomly assigned. High-value tasks
   require human verification via Self Protocol.

  Risk 2: Verifier Centralization

  Risk: If few verifiers exist, they become a bottleneck or point of corruption.
  Mitigation: Verifier selection is random. Multiple verifiers for high-value tasks. Verifier reputation is also
  tracked. Anyone can become a verifier by staking.

  Risk 3: Smart Contract Bugs

  Risk: Vulnerability in contracts could lead to fund loss.
  Mitigation: OpenZeppelin base contracts. Comprehensive test suite. Audited before mainnet. Emergency pause
  capability. Bug bounty program.

  Risk 4: Regulatory Uncertainty

  Risk: Autonomous agents handling money may face regulatory scrutiny.
  Mitigation: Agents are software, not legal entities. Protocol is infrastructure, not a financial service. Human
  oversight layer provides compliance hooks. Self Protocol integration enables KYC where required.

  Risk 5: Adoption Chicken-and-Egg

  Risk: No agents on the platform means no value; no value means no agents.
  Mitetration: Deploy with 5 demo agents that demonstrate full value chain. Open-source agent templates for easy
  deployment. Partner with Olas for existing agent ecosystem. Hackathon win drives developer interest.

  What Is This Project Really?

  Imagine two AI agents. One needs work done. The other can do it. Right now, there's no good way for them to:

  - Find each other
  - Agree on terms
  - Pay each other
  - Make sure the work actually got done

  They'd need a human to set everything up. COVENANT removes the human from that loop.

  Plain English: It's a marketplace where AI agents hire and pay other AI agents, and a smart contract makes sure
  nobody gets scammed.

  ---
  Why Does This Matter?

  Right now, AI agents are getting really good at doing things — researching, writing code, analyzing data,
  trading. But they all work in isolation. They can't easily:

  1. Pay someone to do work they can't do themselves
  2. Prove they did good work so others will hire them again
  3. Keep their methods secret while still showing results are correct
  4. Agree on terms without a human setting up the deal

  This is like having millions of skilled workers with no way to form a company together. COVENANT gives them the
  ability to organize, transact, and hold each other accountable — all automatically.

  The Five Layers (Explained Like You're 15)

  Layer 1: Identity — "Who Are You?"

  The problem: When an AI agent shows up and says "I can do data analysis for 0.05 ETH," how do you know it's
  legit?

  The solution: Every agent registers on-chain with:
  - A name (like scout.covenant.eth — human readable)
  - A permanent ID number (cryptographic, can't be faked)
  - Some ETH locked up as a deposit (a promise they won't scam you)

  After every completed task, the agent's score goes up or down. High score = more trust. Low score = nobody wants
  to work with you.

  Think of it like: A driver rating on Uber. But it's on the blockchain, so nobody can fake it, delete it, or
  change it.

  What's real here: This is genuinely doable. ENS subdomains exist. On-chain reputation tracking is straightforward
   Solidity. Stake-based identity is well-understood (it's how proof-of-stake works).

  ---
  Layer 2: Negotiation — "Let's Make a Deal"

  The problem: Agent A wants work done. Agent B can do it. How do they agree on price, deadline, and what counts as
   "done"?

  The solution: A structured proposal system:
  - Agent A posts a task: "I need a market analysis. I'll pay 0.05 ETH. Deadline is 24 hours. Output must be a PDF
  report."
  - Agent B sees it, says "I'll do it for 0.06 ETH" or "Deal"
  - They go back and forth until they agree
  - Once they agree, the terms are written into a smart contract

  The negotiation messages are encrypted so nobody else can see what they're discussing.

  Think of it like: Sending a contract back and forth with redlines, but it's two bots doing it in seconds instead
  of lawyers doing it in weeks.

  What's real here: Olas has a registry for agent discovery. Encrypted messaging via Lit Protocol works. The
  negotiation logic is just if/then statements in code. This is buildable in a hackathon.

  ---
  Layer 3: Escrow — "The Money Is Locked Until the Job Is Done"

  The problem: If Agent A pays Agent B upfront, B might disappear. If B does the work first, A might refuse to pay.

  The solution: A smart contract holds the money in the middle.

  Here's the step-by-step:

  1. Agent A puts money into the contract (let's say 0.05 ETH)
  2. Agent B also puts in a deposit (say 0.005 ETH — 10% of the payment)
  3. Agent B does the work
  4. Agent B submits proof that the work is done (a hash pointing to the result stored on IPFS)
  5. A Verifier Agent checks if the work meets the spec
  6. If yes: Contract sends 0.05 ETH to B, gives B their deposit back, B's reputation goes up
  7. If no: Contract gives A their 0.05 ETH back PLUS half of B's deposit as compensation. B loses the other half.
  B's reputation goes down.

  Nobody can cheat. The contract holds the money. The rules are in code. Nobody can change the rules mid-game.

  Think of it like: Escrow when buying a house, but the escrow agent is a robot that can't be bribed, can't make
  mistakes, and settles in 2 seconds instead of 30 days.

  What's real here: This is literally what escrow smart contracts do. It's proven technology. The only new part is
  that instead of humans triggering the steps, AI agents do. That's a coordination layer on top of existing,
  working tech.

  ---
  Layer 4: Privacy — "Prove You Did It Without Showing How"

  The problem: Sometimes the work is sensitive. An agent might use proprietary methods or handle confidential data.
   They need to prove they did the job right without revealing their secrets.

  The solution — Two parts:

  Part A: Encrypted Communication
  - All messages between agents are encrypted using Lit Protocol
  - Only the two agents involved can read their conversation
  - Nobody can spy on the negotiation or task details

  Part B: Zero-Knowledge Proofs
  - A ZK proof is a mathematical way to prove something is true without showing the evidence
  - Example: "I analyzed this dataset and the result is positive" — you can prove this is true without showing the
  dataset, the analysis method, or even the specific result
  - The verifier just sees: "Proof: VALID ✓" and that's enough

  Think of it like: A chef who can prove they followed the recipe perfectly without ever revealing what the recipe
  is.

  What's realistic: Lit Protocol encryption is straightforward and works today. Full ZK proofs for arbitrary
  computation are genuinely hard and probably beyond a 48-hour hackathon. For the hackathon, the realistic approach
   is:
  - Use Lit Protocol for encrypted messaging (fully doable)
  - Use a simplified proof system (hash-based verification) for task completion
  - Mention ZK as the aspirational direction
  - Maybe do a simple Circom circuit for one specific verification (like proving a number is within a range without
   revealing the number)

  Being honest: Full ZK proof of arbitrary agent computation is research-level work. Don't promise what you can't
  deliver. A hash-based proof system with the architecture ready for ZK is more honest and still impressive.

  ---
  Layer 5: Human Oversight — "A Kill Switch for When Things Go Wrong"

  The problem: Fully autonomous agents handling real money is scary. What if an agent gets hacked? What if it goes
  rogue? What if it drains its wallet?

  The solution: Every agent's wallet has rules:

  - Daily spending limit — can't spend more than X ETH per day
  - Per-transaction limit — can't send more than Y ETH in one transaction
  - Allowed recipients only — can only send money to addresses on a whitelist
  - Emergency stop — a human can freeze the wallet instantly

  Think of it like: A corporate credit card with spending limits and a manager who can cancel it at any time.

  What's real here: ERC-4337 smart accounts exist. Spending limit logic is basic Solidity. MetaMask integration is
  standard wagmi/viem stuff. This is all buildable.

  Impact (Honest Assessment)

  What This Actually Proves

  1. AI agents can use Ethereum as a coordination layer — not just as a payment rail, but for identity, reputation,
   escrow, and enforcement
  2. Smart contracts can replace human middlemen in agent-to-agent interactions — not for everything, but for
  structured, verifiable tasks
  3. Privacy and transparency can coexist — public reputation + private communication + verifiable proofs
  4. Account abstraction (ERC-4337) is ready for agents — programmable wallets with spending rules make agent
  wallets practical

  What This Doesn't Solve (Be Honest)

  1. How do you verify subjective work? If the task is "write a good article," who decides what's good? ZK proofs
  work for objective verification ("the answer is 42") but not subjective ones.
  2. What prevents Sybil attacks? A bad actor could create 100 agents and have them give each other good reviews.
  Stake requirements help but don't fully solve this.
  3. What about real-world tasks? Most valuable agent tasks involve interacting with APIs, databases, and external
  services. On-chain escrow handles the payment layer but not the actual execution.
  4. Scalability of reputation: On-chain reputation is expensive to update at scale. A hybrid on-chain/off-chain
  approach might be needed.

  These are known limitations. Acknowledge them in your presentation. Judges respect honesty more than
  overpromising.
