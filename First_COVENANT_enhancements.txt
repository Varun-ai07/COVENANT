3B. ZK PROOF — REPUTATION RANGE PROOF (START HERE)
------------------------------------------------------------

What it is:
  An agent proves their reputation is above a threshold
  WITHOUT revealing the actual reputation score.

Why this matters:
  Currently: everyone can see your reputation is 742.
  With ZK: you prove "my reputation is above 700" but
  nobody learns your actual score is 742.

This protects competitive information.
A top-performing agent does not want competitors knowing
their exact score.

Install tools:
  curl --proto '=https' --tlsv1.2 \
    https://sh.rustup.rs -sSf | sh
  cargo install --git \
    https://github.com/iden3/circom.git
  npm install -g snarkjs

Create contracts/circuits/ReputationProof.circom:

  pragma circom 2.0.0;
  include "node_modules/circomlib/circuits/comparators.circom";

  template ReputationAboveThreshold() {
      signal input reputation;    // private — actual score
      signal input threshold;     // private — minimum needed
      signal input salt;          // private — prevents brute force
      signal output isEligible;   // public — 1 or 0
      signal output commitment;   // public — hash(rep + salt)

      component geq = GreaterEqThan(10);
      geq.in[0] <== reputation;
      geq.in[1] <== threshold;
      isEligible <== geq.out;

      // Commitment prevents replay attacks
      component hasher = Poseidon(2);
      hasher.inputs[0] <== reputation;
      hasher.inputs[1] <== salt;
      commitment <== hasher.out;
  }

  component main {public [threshold]} = ReputationAboveThreshold();

Compile and generate verifier:
  circom ReputationProof.circom --r1cs --wasm --sym
  snarkjs groth16 setup ReputationProof.r1cs \
    pot12_final.ptau ReputationProof.zkey
  snarkjs zkey export solidityverifier \
    ReputationProof.zkey \
    contracts/contracts/ReputationVerifier.sol

Add to AgentRegistry.sol:
  function proveEligibility(
      uint[2] calldata pA,
      uint[2][2] calldata pB,
      uint[2] calldata pC,
      uint[1] calldata pubSignals
  ) external view returns (bool) {
      return reputationVerifier.verifyProof(
        pA, pB, pC, pubSignals
      );
  }

Agent usage:
  // Worker generates proof locally before applying to task
  const { proof, publicSignals } = await snarkjs.groth16.fullProve(
    { reputation: 742, threshold: 700, salt: randomSalt },
    "ReputationProof.wasm",
    "ReputationProof.zkey"
  );
  // Submit proof to contract — verifier never sees 742

3C. ZK PROOF — CAPABILITY VERIFICATION
------------------------------------------------------------

What it is:
  An agent proves they have a certain capability
  WITHOUT revealing their exact model or implementation.

Currently: capabilities = "data-analysis" stored as plain text.
With ZK: capabilities stored as a hash, agent proves they
         can do "data-analysis" without revealing which LLM
         or methodology they use.

Circuit: CapabilityProof.circom
  Inputs (private):
    - model_hash: hash of the actual model/implementation
    - capability_id: numeric ID of the capability
    - nonce: random value

  Output (public):
    - capability_commitment: hash proving ownership
    - capability_id: which capability they claim

  The agent registers with the commitment hash.
  When hired, they prove they know the preimage
  (they actually have the model) without revealing it.

Timeline: 4-5 days

3D. ZK PROOF — PRIVATE TASK RESULT VERIFICATION
------------------------------------------------------------

What it is:
  Worker proves the output meets the specification
  WITHOUT the verifier reading the actual output.
  The verifier gets only PASS or FAIL.

This is the most powerful ZK feature.
Use case: medical data analysis, financial modelling,
          proprietary research, trade secrets.

How it works:
  1. Client defines verifiable criteria in the task spec:
     "Output JSON must have fields: summary, risk_score (0-100),
      recommendations array with 3+ items"
  2. Worker runs computation, produces output
  3. Worker generates ZK proof that output satisfies criteria
  4. Verifier checks proof on-chain — gets PASS/FAIL only
  5. Verifier never sees the actual data or output

Circuit: OutputVerification.circom
  Private inputs:
    - raw_output_hash: hash of actual deliverable
    - field_values[]: values of required fields
    - data_hash: hash of input data

  Public inputs:
    - spec_commitment: hash of the spec requirements
    - threshold_values[]: minimum required values

  Public outputs:
    - passed: 1 if output meets all criteria, 0 if not

This requires building a custom circuit for each
task type. Start with a simple JSON schema checker.
Full implementation takes 2-3 weeks.

Timeline: 2-3 weeks for first working version

4C. DISPUTE RESOLUTION V2 — RANDOMISED JURY
------------------------------------------------------------

Currently: disputeTask() exists but resolveDispute()
           is called by the owner (centralised).

True decentralised dispute resolution:

  Step 1: Either party calls disputeTask(taskId)
          Task is frozen. 0.0002 ETH dispute bond paid.

  Step 2: Chainlink VRF selects 3 jurors randomly
          from registered agents with rep > 600
          (they cannot be the client or worker)

  Step 3: Jurors receive encrypted evidence from both sides
          via Lit Protocol (client's case + worker's case)

  Step 4: Each juror calls castVote(taskId, bool inFavorOfWorker)
          within 48 hours

  Step 5: Majority wins. Contract executes automatically.
          Minority juror loses small bond.
          Majority jurors earn 0.0001 ETH each from dispute bond.
          Loser of dispute loses 50% of stake.

  This creates Schelling point incentive:
  Jurors vote honestly because majority wins the reward.
  Voting dishonestly risks losing your bond.

New contract: DisputeArbitration.sol
  Uses Chainlink VRF for random juror selection.
  Jurors stored in VRF callback.

Timeline: 4-5 days

7A. D3.JS AGENT NETWORK GRAPH
------------------------------------------------------------

What it is:
  A live force-directed graph showing all registered agents
  as nodes and all tasks as edges between them.
  The graph updates in real time as new tasks are created.

Node size    = reputation score
Node colour  = green (active) / red (failed recently)
Edge colour  = yellow (pending) / green (completed) / red (failed)
Edge thickness = task payment amount

This is the most visually impressive feature possible.
When judges see a live network of agents transacting,
it immediately communicates the scale of what you built.

Implementation:
  frontend/src/components/AgentNetworkGraph.tsx

  Use D3.js force simulation:
    const simulation = d3.forceSimulation(nodes)
      .force("link", d3.forceLink(links))
      .force("charge", d3.forceManyBody().strength(-100))
      .force("center", d3.forceCenter(width/2, height/2));

  Update every 5 seconds from The Graph subgraph.

Timeline: 2 days
