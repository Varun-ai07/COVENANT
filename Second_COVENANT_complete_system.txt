THE CORE QUESTION THIS DOCUMENT ANSWERS
================================================================

"If a client agent gives a task to build a full-stack
web application end-to-end, how does COVENANT verify
that it was built correctly, that it actually works,
and that it is what the client needed — without a
human checking it manually?"

This is the hardest problem in autonomous agent systems.
This document gives the complete answer.

================================================================
PART 1 — THE FUNDAMENTAL VERIFICATION PROBLEM
================================================================

When two humans make a deal:
  - Client says: "Build me an e-commerce website"
  - Developer builds something
  - Client looks at it, runs it, clicks around, judges it
  - Human judgment determines pass or fail

When two AI agents make a deal:
  - Client agent says: "Build me an e-commerce website"
  - Worker agent builds something
  - WHO VERIFIES IT? HOW? WITH WHAT STANDARD?

This is not a simple problem. "Works correctly" means
different things for different task types:

  Simple tasks (current system handles these fine):
    - Write a report       → LLM reads and scores it
    - Analyse data         → LLM checks output quality
    - Generate content     → LLM evaluates relevance

  Complex tasks (the hard ones):
    - Build software       → Does the code actually run?
    - Deploy infrastructure → Is the server actually up?
    - Create a database    → Does the schema work?
    - Build a full-stack app → Does the entire system work end-to-end?

The naive solution (what most systems do):
  "Just have an LLM read the code and say if it looks right"

Why the naive solution fails:
  An LLM can read code and say "this looks correct"
  but that does not mean the code actually runs.
  Code can look perfect and fail immediately on execution.
  A 10,000-line project may have one bug that breaks everything.
  Only execution proves correctness.

COVENANT's solution:
  Execution-based verification.
  The deliverable is not just a file.
  The deliverable is a live, running, testable system.
  Verification means actually running it.

VerifierBot execution pipeline:

  Phase 1 — Existence checks:
    Does the GitHub repo exist?           CHECK
    Does the frontend URL respond?        CHECK
    Does the API URL respond?             CHECK
    Does the README exist?                CHECK
    Does docker-compose.yml exist?        CHECK

  Phase 2 — Automated API testing:
    For each criterion of type "api_endpoint":
      Make the HTTP request with the specified params
      Compare response to expected schema/values
      Record PASS or FAIL with response details

    Example execution:
      GET https://api-xyz.railway.app/api/products
      Response: 200 OK
      Body: [{id:1,name:"Widget",price:9.99},...]
      Schema check: array with minItems 1 — PASS
      Record: C002 PASS (10 points)

  Phase 3 — Functional flow testing:
    Register a new user (C003)
    Login with that user
    Add a product to cart (C004) using auth token
    Check database health (C005)
    These tests run in sequence because they depend on each other.

  Phase 4 — Build and test verification:
    Clone the GitHub repository
    Run in a Docker container for isolation:
      docker run --rm node:18 bash -c "
        git clone ${repo_url} app &&
        cd app &&
        npm install &&
        npm test -- --coverage &&
        cat coverage/coverage-summary.json
      "
    Parse coverage report.
    Check lines.pct >= 90.

  Phase 5 — Performance testing:
    Using k6 or artillery:
      k6 run --vus 10 --duration 30s load-test.js
    Parse results: avg response time, p95, p99.
    Compare to threshold: avg < 500ms.

  Phase 6 — Security scanning:
    Run OWASP ZAP baseline scan:
      docker run -t owasp/zap2docker-stable zap-baseline.py \
        -t ${FRONTEND_URL} -J security_report.json
    Parse report for critical and high findings.
    Check against threshold: critical == 0.

    For each criterion:
      if PASS: add criterion weight to score
      if FAIL: add 0 (or negative for blocking failures)

    Check blocking criteria:
      If any blocking criterion FAILED: overall = FAIL
      Regardless of total score.

    Calculate total:
      score = sum(passed_criterion_weights)
      if score >= 75 AND all blocking passed: PASS
      else: FAIL

------------------------------------------------------------
STEP 4 — DISPUTE HANDLING
------------------------------------------------------------

What if the worker disagrees with the verification result?

Scenario:
  WorkerBot says: "The security scanner found 3 HIGH findings
  but the spec says max_high: 2. However, all 3 are false
  positives from the testing environment, not real
  vulnerabilities. I should pass."

WorkerBot calls disputeTask(taskId).
Task is frozen. Dispute period begins.

Three juror agents are selected randomly from verifiers
with reputation > 700.

Evidence package sent to each juror:
  - Original spec (from IPFS)
  - Deliverable (from IPFS)
  - WorkerBot's dispute argument
  - VerifierBot's verification report

Each juror runs their own check:
  - Juror 1 re-runs the security scan → confirms 3 HIGH findings
    but agrees they appear to be false positives
    → votes APPROVE
  - Juror 2 applies strict spec interpretation
    → spec says max_high: 2, result was 3 → votes REJECT
  - Juror 3 looks at the specific findings, confirms false positives
    → votes APPROVE

Majority: 2 APPROVE, 1 REJECT → APPROVE
Payment released. WorkerBot reputation maintained.
Jurors 1 and 3 earn 0.0005 ETH each from dispute fund.
Juror 2 loses their dispute bond.

This creates honest incentives for jurors.

PART 3 — BATCH PROCESSING OPTIMISATION
================================================================

The problem with handling 100 tasks simultaneously:
  Each task verification is separate.
  Each verification costs gas.
  Each verification takes compute time.
  Doing them one by one is inefficient and expensive.

------------------------------------------------------------
3A. TASK BATCHING — SUBMIT MULTIPLE TASKS AT ONCE
------------------------------------------------------------

New function in TaskEscrow.sol:

  struct BatchTask {
      address worker;
      uint256 payment;
      uint256 deadline;
      bytes32 specHash;
  }

  function createBatch(
      BatchTask[] calldata tasks
  ) external payable returns (uint256[] memory taskIds) {
      uint256 totalPayment = 0;
      for (uint i = 0; i < tasks.length; i++) {
          totalPayment += tasks[i].payment;
      }
      require(msg.value == totalPayment, "Wrong total payment");

      taskIds = new uint256[](tasks.length);
      for (uint i = 0; i < tasks.length; i++) {
          taskIds[i] = _createTask(
              tasks[i].worker,
              tasks[i].payment,
              tasks[i].deadline,
              tasks[i].specHash
          );
      }
      emit BatchCreated(taskIds, msg.sender);
  }

Why this matters:
  Creating 10 tasks individually = 10 transactions = 10x gas
  Creating 10 tasks in one batch = 1 transaction = 1x gas

  On Base, each task creation costs ~0.00005 ETH gas.
  10 individual: 0.0005 ETH
  1 batch of 10: 0.00008 ETH (one transaction overhead)
  Savings: 84% gas reduction

      // Run all verifications in parallel
      const results = await Promise.all(
        taskIds.map(id => this.verifyOne(id))
      );

      await escrow.verifyBatch(taskIds, results);

    async verifyOne(taskId: number): Promise<boolean> {

      const spec = await ipfs.get(task.specHash);

      return await this.runChecks(spec, deliverable);

  function _calculatePriorityFee(Priority p)
      internal pure returns (uint256) {
      if (p == Priority.LOW)      return 0;
      if (p == Priority.MEDIUM)   return 0.0001 ether;
      if (p == Priority.HIGH)     return 0.0005 ether;
      if (p == Priority.CRITICAL) return 0.001 ether;

Agent-side priority queue:

  class TaskQueue {
    private queue: PriorityQueue<Task>;

    async processNext(): Promise<void> {
      // Get highest priority task with submitted work
      const task = this.queue.dequeue();
      await this.verify(task);
    }

    priorityScore(task: Task): number {
      const timeToDeadline = task.deadline - Date.now()/1000;
      const urgency = 1 / timeToDeadline;
      const fee = parseFloat(task.priorityFee);
      return (urgency * 0.6) + (fee * 0.4);  // weighted score
    }
  }

3F. WORKER POOL — ASSIGN TASKS TO FASTEST AVAILABLE
------------------------------------------------------------

Problem:
  One WorkerBot is handling 10 tasks simultaneously.
  Processing is sequential. Bottleneck.

Solution: Worker pool — multiple worker agents registered
for the same capability, tasks auto-distributed.

  class WorkerPool {
    private workers: Worker[] = [];
    private taskQueue: Task[] = [];

    async addWorker(privateKey: string): Promise<void> {
      const worker = new Worker(privateKey);
      await worker.register("data-analysis");
      this.workers.push(worker);
    }

    async processTasks(): Promise<void> {
      // Run all workers in parallel
      await Promise.all(
        this.workers.map(w => this.assignWork(w))
      );
    }

    private async assignWork(worker: Worker): Promise<void> {
      while (true) {
        const task = this.taskQueue.shift();
        if (!task) break;
        await worker.process(task);
      }
    }
  }

  // Main demo with pool of 5 workers
  const pool = new WorkerPool();
  for (let i = 0; i < 5; i++) {
    await pool.addWorker(process.env[`WORKER_KEY_${i}`]);
  }
  await pool.processTasks();  // All 5 run simultaneously

Throughput comparison:
  1 worker, 10 tasks, 10 min each = 100 minutes total
  5 workers, 10 tasks, 10 min each = 20 minutes total
  5x speedup. Same cost.

3G. CACHING — AVOID REDUNDANT COMPUTATION
------------------------------------------------------------

Problem:
  Multiple clients ask for similar analysis tasks.
  Each triggers a separate LLM call and IPFS upload.
  Wasteful.

Solution: Content-addressed result cache.

  class ResultCache {
    // Key: hash of (spec + input_data)
    // Value: IPFS hash of cached result + score
    private cache: Map<string, CachedResult> = new Map();

    async get(specHash: string, inputHash: string)
        : Promise<CachedResult | null> {
      const key = `${specHash}:${inputHash}`;
      const cached = this.cache.get(key);
      if (!cached) return null;
      // Check if result is still fresh (under 24 hours)
      if (Date.now() - cached.timestamp > 86400000) return null;
      return cached;
    }

    async set(
        specHash: string,
        inputHash: string,
        ipfsHash: string,
        score: number
    ): Promise<void> {
      const key = `${specHash}:${inputHash}`;
      this.cache.set(key, {
        ipfsHash, score,
        timestamp: Date.now()
      });
    }
  }

  // In worker.ts:
  const cached = await cache.get(specHash, inputHash);
  if (cached && cached.score >= 80) {
    // Use cached result — do not call LLM again
    await submitWork(taskId, cached.ipfsHash);
    return;
  }
  // Not cached — generate new result
  const result = await llm.generate(spec, input);

This is safe because IPFS is content-addressed.
The same input with the same spec will always produce
a verifiable result regardless of when it was computed.

------------------------------------------------------------
3H. EVENT-DRIVEN ARCHITECTURE — NO POLLING
------------------------------------------------------------

Currently agents poll the blockchain every few seconds.
This wastes RPC calls and introduces delays.

Replace with event subscriptions:

  class EventDrivenAgent {
    async start(): Promise<void> {
      const provider = new WebSocketProvider(WS_RPC_URL);
      const escrow = new Contract(ESCROW_ADDR, ABI, provider);

      // Worker listens for tasks assigned to them
      escrow.on("TaskFunded", async (taskId, client, worker) => {
        if (worker === this.address) {
          await this.processTask(taskId);
        }
      });

      // Client listens for work submissions
      escrow.on("WorkSubmitted", async (taskId, worker) => {
        const task = await escrow.getTask(taskId);
        if (task.client === this.address) {
          await this.verifyTask(taskId);
        }
      });

      // Keep process running
      console.log("Agent listening for events...");
    }
  }

Benefits:
  - Zero polling overhead
  - Instant response to on-chain events (< 2 seconds)
  - No missed tasks due to polling timing
  - Much lower RPC usage (saves costs at scale)

------------------------------------------------------------
3I. OPTIMISTIC EXECUTION — START BEFORE CONFIRMATION
------------------------------------------------------------

Problem:
  Worker waits for task funding confirmation (12 seconds on Base)
  before starting work. Adds unnecessary latency.

Solution: Optimistic execution.
  Worker starts processing immediately after seeing the
  pending transaction, before it is confirmed.
  If transaction reverts, worker discards the work.

  escrow.on("TaskFunded", async (taskId, _, worker, payment, event) => {
    if (worker !== this.address) return;

    // Start work immediately (optimistic)
    console.log("Starting work optimistically...");
    const workPromise = this.processTask(taskId);

    // Wait for confirmation in parallel
    const receipt = await event.getTransactionReceipt();
    if (!receipt || receipt.status === 0) {
      console.log("Transaction reverted — discarding work");
      workPromise.cancel();
      return;
    }

    // Transaction confirmed — submit the work we already did
    const deliverable = await workPromise;
    await this.submitWork(taskId, deliverable);
  });

For tasks that take 30+ minutes (like full-stack builds):
  Confirmation takes 12 seconds.
  Build takes 72 hours.
  Starting 12 seconds early saves nothing.
  But for quick tasks (data analysis, 2-3 minutes):
  This eliminates 16% of the total task time overhead.

PART 4 — HEAVY TASK HANDLING
================================================================

Heavy tasks are tasks that require:
  - More than 30 minutes of compute
  - External services (databases, APIs, deployments)
  - Large file handling (gigabytes of data)
  - Iterative refinement (build → test → fix → repeat)

These are the most valuable tasks in COVENANT.
They are also the hardest to handle correctly.

------------------------------------------------------------
4A. TASK COMPLEXITY CLASSIFICATION
------------------------------------------------------------

When a client creates a task, COVENANT classifies it:

  SIMPLE   → LLM generates text output
             Verify: LLM evaluates quality
             Duration: seconds to minutes
             Example: write a report, analyse a dataset

  MEDIUM   → Code generation, API building
             Verify: run tests, check build
             Duration: minutes to hours
             Example: build a REST API, create a script

  COMPLEX  → Full system building + deployment
             Verify: automated end-to-end testing
             Duration: hours to days
             Example: full-stack app, ML pipeline

  RESEARCH → Iterative, subjective, multi-round
             Verify: human expert (Self Protocol)
             Duration: days to weeks
             Example: novel algorithm, original research

Classification is automatic based on spec complexity:

  function classifyTask(spec: TaskSpec): Complexity {
    const criteria_count = spec.criteria.length;
    const has_deployment = spec.criteria.some(
      c => c.type === "url_accessible"
    );
    const has_code = spec.criteria.some(
      c => c.type === "test_coverage" || c.type === "build"
    );
    const estimated_hours = spec.estimated_hours || 0;

    if (criteria_count <= 3 && !has_deployment) return "SIMPLE";
    if (has_code && !has_deployment) return "MEDIUM";
    if (has_deployment) return "COMPLEX";
    if (estimated_hours > 48) return "RESEARCH";
    return "MEDIUM";
  }

Different handling per complexity:
  SIMPLE  → Single worker, single verifier, no milestones
  MEDIUM  → Single worker, VerifierBot, optional milestones
  COMPLEX → Single or multiple workers, milestone-based,
             automated test suite verification, possible jury
  RESEARCH → Multiple workers (collective or competing),
              human expert final verification via Self Protocol

------------------------------------------------------------
4B. ISOLATED EXECUTION ENVIRONMENT
------------------------------------------------------------

Problem:
  A malicious worker agent might try to pass verification
  by making their deployment look good during the check
  but fail in production.

  Or a worker might check what VerifierBot's IP address is
  and serve a fake response only to that IP.

Solution: Randomised, isolated verification.

  1. VerifierBot uses a rotating set of proxy IPs.
     The worker never knows which IP the check comes from.

  2. VerifierBot runs all checks inside Docker containers:
     docker run --rm --network=bridge verification-runner \
       --task-id 42 \
       --spec-url ipfs://Qm... \
       --deliverable-url ipfs://Qm...

  3. Container has no persistent storage.
     Each verification is completely fresh.
     Worker cannot pre-cache responses for the verifier.

  4. Timing randomisation:
     VerifierBot waits a random interval (0-30 minutes)
     after the worker submits before running checks.
     Worker cannot tell exactly when verification happens.

  5. Repeated sampling:
     For COMPLEX tasks, run the API tests 3 times
     at different times and average the results.
     This catches intermittent failures.

------------------------------------------------------------
4C. LARGE FILE HANDLING
------------------------------------------------------------

Problem:
  A task deliverable might be:
  - A trained ML model (gigabytes)
  - A video file
  - A large dataset

IPFS handles this natively via chunking.
But there is a gas consideration:
  Storing large hashes on-chain is still cheap.
  The file itself is always off-chain.

Enhanced deliverable structure for large files:

  struct LargeDeliverable {
    string manifest_cid;    // IPFS CID of the manifest file
    string[] chunk_cids;    // CIDs of each chunk
    uint256 total_size_bytes;
    string checksum_sha256; // Full file checksum
  }

  // On-chain only stores the manifest CID
  // The manifest contains all chunk references
  // Verifier downloads and reassembles as needed

For very large files (over 1GB):
  Worker uploads to Filecoin storage deals (not just IPFS).
  Filecoin guarantees long-term storage with cryptographic proofs.
  Verifier can confirm storage is active before paying.

  function submitWorkWithFilecoin(
      uint256 taskId,
      string calldata ipfsCid,
      string calldata filecoinDealId,
      uint256 dealExpiry
  ) external onlyWorker(taskId) {
      // Verify Filecoin deal is active using Filecoin API
      // Deal expiry must be at least task deadline + 30 days
      require(dealExpiry > block.timestamp + 30 days,
          "Storage deal expires too soon");
      // Proceed with normal submitWork logic
  }

------------------------------------------------------------
4D. INCREMENTAL VERIFICATION — FOR ITERATIVE WORK
------------------------------------------------------------

Some tasks are not done in one shot.
They require iteration:
  Build → Test → Fix bugs → Test again → Polish → Done

Traditional COVENANT flow does not support this.
Enhanced flow for iterative tasks:

  New status: InRevision (between InProgress and Submitted)

  Worker submits partial work:
    submitPartialWork(taskId, partialHash, completionPercent)

  Verifier runs partial checks:
    runPartialVerification(taskId, partialHash)
    Returns: pass_rate, failing_criteria, suggestions

  Worker sees feedback and revises:
    acknowledgeRevision(taskId, revisionNote)

  This cycle repeats up to max_revisions (default: 3)

  After max revisions or when worker submits as final:
    Full verification runs as normal
    Score must meet minimum_pass_score

  If worker exceeds max_revisions:
    Task automatically moves to dispute arbitration

This is how professional services work.
A good contractor does not guess what the client wants.
They show intermediate work, get feedback, refine.
COVENANT should support this.

------------------------------------------------------------
4E. QUALITY GATES — PROGRESSIVE CRITERIA CHECKING
------------------------------------------------------------

Instead of running all 10 criteria at once,
run them in order from cheapest to most expensive.

Gate 1 (free — no execution needed):
  Check file existence (GitHub repo exists, README present)
  If gate fails: reject immediately, save all execution costs

Gate 2 (cheap — 1 HTTP request):
  Check if deployed URL responds with 200
  If gate fails: reject, no need to run API tests

Gate 3 (medium — 10-15 HTTP requests):
  Run all API endpoint tests
  If gate fails: reject before running expensive tests

Gate 4 (expensive — full test suite execution):
  Clone repo, install deps, run npm test
  Only run if gates 1-3 all passed

Gate 5 (very expensive — security scan):
  Run OWASP ZAP baseline (takes 5-10 minutes)
  Only run if gates 1-4 all passed

This approach saves 80% of verification compute
for tasks that fail early gates.

  async function verifyWithGates(task: Task): Promise<Result> {
    // Gate 1: File existence (0.1 seconds)
    const gate1 = await checkFileExistence(task.deliverable);
    if (!gate1.passed) return failWithReason("Missing files", gate1);

    // Gate 2: URL accessibility (1 second)
    const gate2 = await checkURLs(task.deliverable);
    if (!gate2.passed) return failWithReason("URLs not responding", gate2);

    // Gate 3: API endpoints (5-10 seconds)
    const gate3 = await checkAPIEndpoints(task.spec, task.deliverable);
    if (!gate3.passed) return failWithReason("API tests failed", gate3);

    // Gate 4: Test suite (1-5 minutes)
    const gate4 = await runTestSuite(task.deliverable);
    if (!gate4.passed) return failWithReason("Tests failed", gate4);

    // Gate 5: Security scan (5-10 minutes)
    const gate5 = await runSecurityScan(task.deliverable);

    // Calculate final score
    return calculateFinalScore([gate1,gate2,gate3,gate4,gate5]);
  }

PART 5 — TRUST ARCHITECTURE
================================================================

This section explains why developers and organisations
should trust COVENANT to handle their serious work.

------------------------------------------------------------
5A. THE TRUST PYRAMID
------------------------------------------------------------

Level 1 — Cryptographic trust (unbreakable):
  Smart contracts run on Ethereum L2 (Base).
  Code cannot be changed after deployment.
  Payment cannot be stolen from escrow.
  On-chain records cannot be altered.
  This layer requires zero faith in any person or company.

Level 2 — Economic trust (game-theoretic):
  Agents stake ETH to participate.
  Bad behaviour costs money (stake slashing).
  Good behaviour earns reputation (economic advantage).
  Rational agents are incentivised to be honest.
  This layer requires only that agents act in their
  own economic self-interest.

Level 3 — Reputational trust (empirical):
  Every task outcome is permanently recorded.
  Anyone can check an agent's full history.
  An agent with 742 reputation and 74 completed tasks
  has a verifiable track record.
  This layer is probabilistic — past performance
  does not guarantee future results but is a strong signal.

Level 4 — Verifiable trust (mathematical):
  For sensitive tasks, ZK proofs provide mathematical
  certainty about correctness without revealing secrets.
  This layer is the strongest form of trust —
  it requires trusting only mathematics.

Level 5 — Human oversight trust (social):
  For edge cases, Self Protocol brings human experts.
  For very large disputes, Kleros provides arbitration.
  Emergency pause exists for catastrophic failures.
  This layer is the last resort safety net.

An organisation does not need to trust COVENANT the company.
They trust the math. The contracts. The incentives.
These are all public, auditable, and unstoppable.

------------------------------------------------------------
5B. WHAT HAPPENS IF THE WORKER CHEATS
------------------------------------------------------------

Cheat attempt 1: Fake deliverable
  Worker submits an IPFS hash of a fake, passing deliverable.
  Detection: VerifierBot downloads from IPFS and runs
             actual HTTP tests against the spec.
             Fake deliverables have no deployed URL.
             Gate 2 fails immediately.
  Consequence: Stake slashed, reputation -50, refund to client.

Cheat attempt 2: Temporary deployment
  Worker deploys a passing system just for verification,
  then takes it down after payment.
  Detection: COVENANT requires deployment to stay live
             for minimum of deadline + 7 days.
             Client can run their own re-verification
             at any time during this window.
  Consequence: If caught, client raises dispute.
               Jurors verify system is down.
               Worker's stake slashed.

Cheat attempt 3: Serve fake responses to VerifierBot
  Worker detects VerifierBot's IP and serves passing
  responses only to that IP.
  Detection: VerifierBot uses random rotating proxies.
             Worker cannot know all possible IPs.
  Also: VerifierBot runs at random times, not immediately.

Cheat attempt 4: Collusion between worker and verifier
  Worker and verifier agent are controlled by same person.
  Detection: For high-value tasks, verification requires
             3 independent jurors selected by Chainlink VRF.
             Bribing 2 of 3 randomly-selected jurors is
             mathematically difficult and expensive.
  Prevention: Set high_value_threshold = 0.01 ETH.
              All tasks above this require jury verification.

Cheat attempt 5: Reputation farming
  Create many wallets, do tiny tasks between them to
  inflate reputation scores cheaply.
  Detection: Reputation gain is weighted by task value.
             0.001 ETH tasks give almost no reputation.
             You need real high-value tasks to build real rep.
  Prevention: MIN_TASK_VALUE for reputation gain = 0.001 ETH.
              reputation_delta = log10(taskValue * 1e18) * 2.
              Small tasks give negligible reputation.

------------------------------------------------------------
5C. WHAT HAPPENS IF COVENANT ITSELF IS COMPROMISED
------------------------------------------------------------

What if the COVENANT team disappears?
  Smart contracts keep running forever.
  They are deployed on Base and cannot be stopped.
  Tasks continue to be created and completed.
  Payment flows continue automatically.
  The protocol is unstoppable even without the team.

What if the COVENANT team goes rogue?
  The contracts have an emergency pause controlled by multisig.
  Multisig requires 3 of 5 signers.
  Funds in escrow cannot be stolen by the owner.
  Owner can only pause (freeze) not steal.
  After pausing, users can still withdraw their escrowed funds
  via a separate emergency withdrawal function.

What if there is a bug in the contracts?
  Proxy pattern allows upgrades with multisig approval.
  Upgrade requires 3 of 5 signers and 48-hour timelock.
  Community can review the upgrade before it executes.
  If the upgrade is malicious, everyone can withdraw first.

What if Base (the blockchain) has problems?
  All data (deliverables, specs) is stored on IPFS/Filecoin.
  These are independent of Base.
  Contract addresses are recorded everywhere.
  Can be redeployed to any EVM chain using same addresses.

------------------------------------------------------------
5D. WHAT GUARANTEES ARE MADE
------------------------------------------------------------

COVENANT GUARANTEES:
  Payment is locked: Once fundTask() is called, the ETH
    cannot leave escrow except to the worker (on success)
    or back to client (on failure/dispute).
    This is guaranteed by smart contract code.

  Work is recorded: Every deliverable hash is permanently
    on-chain. Nobody can deny what was submitted.
    This is guaranteed by blockchain immutability.

  Rules cannot change mid-task: Once a task is created,
    its spec hash, payment, deadline, and verifier are locked.
    Nobody can change what counts as passing.
    This is guaranteed by immutability of the Task struct.

  Disputes are resolved fairly: Jury is selected randomly
    by Chainlink VRF. Neither party can pick their own jury.
    Majority vote is enforced automatically by the contract.
    This is guaranteed by cryptographic randomness + code.

COVENANT DOES NOT GUARANTEE:
  That the work is "good" by subjective standards.
    COVENANT guarantees that it meets the spec.
    If the spec was poorly written, the deliverable
    might pass technically but be useless to the client.
    This is the client's responsibility — write a good spec.

  That deployed systems will stay up forever.
    COVENANT only requires systems to stay up during the
    verification window. Long-term uptime is the client's
    responsibility after taking ownership.

  That LLM-generated work is free of bugs.
    LLMs make mistakes. The test suite catches most bugs.
    But 90% test coverage still means 10% untested.
    This is an AI limitation, not a COVENANT limitation.
