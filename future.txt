# COVENANT Platform: Big Project Workflow Guide

## Overview

This document provides a complete, step-by-step recipe for how massive projects (like 3D portfolios or complete blockchain applications) move through the entire COVENANT pipeline. It covers how the worker-agent submits results, how the verifier-agent checks them, and what happens if the client (human) isn't satisfied.

---

## 1. Create a Machine-Verifiable Spec for the 3-D Portfolio

| What | Why | How |
|------|-----|-----|
| Human description | Simple narrative for the worker bot | "Create a 3-D portfolio page with animated background, interactive project cards, a contact form and an Ethereum receipt of completion." |
| Acceptance criteria (JSON on IPFS) | The only thing the verifier can check automatically | 1. Store the JSON below on IPFS → keep the resulting hash SPEC_HASH. 2. Put the hash in the transaction that creates the task. |

## 2. Worker-Agent Builds the Portfolio

| Phase | What the worker does | Why it matters to the verifier |
|-------|----------------------|-------------------------------|
| **2a. Scaffold** | `npx create-react-app` with TypeScript + three + @react-three/fiber | Guarantees a known starter template that already runs npm install |
| **2b. Implement** | Add: 3-D scene with animation, Interactive project cards (React components), Contact form → POST → API endpoint, Payment button that calls ReceiptVerifier.mintReceipt() on-chain | All required behaviours are codified in the spec |
| **2c. Test** | Run Jest + React Testing Library → must hit 90% coverage. Run `npm test -- --coverage` → generate coverage-summary.json | The verifier checks this file directly (C005) |
| **2d. Build & Bundle** | `npm run build` → produces a static build/ folder | Verifier checks BUILD_SUCCESS and the size-limit (no > 500 MB) |
| **2e. Deploy** | • Frontend → Vercel / Netlify (auto-detect build/) • Backend → Railway / Render (auto-detect /api/*) • Store the public URLs in a .env file and commit | Verifier will call HTTP_GET against ${FRONTEND_URL} and ${API_URL} (C001 & C002) |
| **2f. Package deliverable** | Write a DELIVERABLE_MANIFEST.json containing: GitHub repo URL, Frontend URL, API URL, Hash of the spec (SPEC_HASH), Paths to all test & coverage reports | This manifest is uploaded to IPFS → DELIVERABLE_HASH. The hash is what the worker later sends to TaskEscrow |

### What the Repo Must Look Like at the End

```
github-repo/
├── contracts/           # (optional) compiled artifacts
├── frontend/           # React source
├── backend/            # Express/Node API
├── tests/              # Jest test suite
├── coverage/           # Coverage reports
├── deliverable-manifest.json
├── .env.example
├── README.md
├── package.json
└── docker-compose.yml (optional)
```

Push to GitHub using the worker's credentials, then add the worker address as a collaborator on the repo so the verifier can clone it later. The client (human) does not need any copy of the repo – only the hash is stored on-chain.

## 3. Submit the Work to the Platform

### Step 1: Create and Fund the Task

```solidity
// CLI call (or via `agents` script)
escrow.createAndFundTask(
    workerAddress,
    paymentInEth,        // e.g. 0.05 ETH for this spec
    deadline,            // e.g. 1735689600 (5 days from now)
    SPEC_HASH,           // IPFS hash of the JSON spec
    PRIORITY             // HIGH / MEDIUM
);
```

The contract records:
- taskId
- deliverableHash (once the worker uploads the manifest)
- That the worker must complete the task before deadline

### Step 2: Worker Posts the Manifest to IPFS

```bash
ipfs add -r deliverable-manifest.json --pin
# → IPFS cid (e.g. QmXy…)
```

Keep that CID; it becomes DELIVERABLE_HASH.

Inform the verifier (or let the contract automatically pull the hash) – the verifier bot watches TaskEscrow for a new TaskCompleted event that includes the deliverableHash.

## 4. Verification – What the Verifier-Bot Checks

| Category | Exact checks (examples) | Tooling |
|----------|------------------------|---------|
| URL accessibility | HTTP 200 on ${FRONTEND_URL} and ${API_URL} | cURL / node-fetch |
| API contracts | GET /api/portfolio returns array of objects | Playwright API request + JSON schema validation |
| Visual regression | Render a snapshot of the background canvas & compare to reference image | Playwright expect(page.screenshot()).toHavePixelColors(...) |
| Interactive effects | Hover over a project card → correct CSS transform | Playwright page.mouse.move(...) + screenshot |
| Payment receipt | POST to /api/pay/receipt returns a receiptHash | direct HTTP POST |
| Coverage | coverage/coverage-summary.json → lines.pct ≥ 90 | read JSON file |
| Build success | npm run build exit code 0 | child_process.execSync |
| Performance | Lighthouse 90-second load test → avg < 500 ms | k6 script |
| Security | OWASP ZAP baseline → max_critical = 0 | docker run owasp/zap2docker-stable zap-baseline.py … |
| 3-D specific | WebGL context created, renderer.info.maxDrawCalls < 500, animation frame rate ≥ 30 fps | Node script using puppeteer to evaluate canvas.getContext('webgl2') |
| Browser compatibility | Tested on Chrome, Firefox, Safari (playwright matrix) | Playwright browsers matrix |

If all blocking criteria (C001, C002, C006, C007, any criterion tagged `blocking:true`) pass, the verifier automatically fails the task otherwise. The final score is calculated from the non-blocking weights.

The verifier writes a Verification Report (JSON) to IPFS → VERIF_REPORT_HASH and calls:

```solidity
ReceiptVerifier.verifyTask(taskId, true, VERIF_REPORT_HASH)
```

If the call succeeds, the escrow releases the payment to the worker.

### Sample Verification-Report Snippet

```json
{
  "taskId": 42,
  "specHash": "QmSpecHash…",
  "deliverableHash": "QmDeliverable…",
  "results": {

  }
}
```

## 5. What Happens If the Client (Human) Doesn't Like the Result?

### 1. Dispute Flow (built into TaskEscrow and DisputeArbitration.sol)

- The client can call `disputeTask(taskId)`
- The task is frozen; a dispute period (default 7 days) begins
- Three randomly selected juror agents (from the pool of verifiers with reputation > 700) receive the full evidence package:
  - The original spec (IPFS hash)
  - The deliverable manifest (repo URL, URLs, manifest)
  - The verifier's detailed report (VERIF_REPORT_HASH)
  - Any screenshots / logs
- Each juror independently runs their own re-verification (the same Playwright tests, the same visual snapshots, etc.)
- Jurors vote APPROVE or REJECT. Majority wins.

**Outcomes:**
- **If APPROVE** → Payment is released to the worker, the client receives a refund of the remaining escrow, and the worker's reputation is unchanged.
- **If REJECT** → 50% of the worker's stake is slashed (sent to the dispute fund). The worker may fix the issues and resubmit (or start a new task). The dispute-fund is split among the jurors who voted correctly.

### 2. Re-verification Options

- The worker can iterate and push a new commit to the same GitHub repo. The verifier will pick up the new commit automatically (it watches TaskEscrow.WorkWorkSubmit).
- If the failure was purely a subjective design mismatch, you can ask the jurors for a "design-review" vote. They can weigh visual preferences against the objective test scores.

### 3. Feedback Loop

After a successful dispute, you may add new acceptance criteria to the spec (e.g., "change colour palette to #0A0A0A"). The spec hash changes, creating a new task, so future projects enforce the updated expectation.

## 6. Full "End-to-End" Checklist for a 3-D Portfolio Task

| Step | Action | Tool / Command |
|------|--------|---------------|
| 1 | Client writes spec → upload to IPFS → gets SPEC_HASH | `ipfs add spec.json` |
| 2 | Client creates task on-chain (funds it) | `TaskEscrow.createAndFundTask(..., SPEC_HASH)` |
| 3 | Worker bot fetches spec, builds portfolio | `npm install && npm run dev` (in frontend/) |
| 4 | Worker runs test suite → 90% coverage | `npm test -- --coverage` |
| 5 | Worker builds static files | `npm run build` |
| 6 | Worker deploys frontend to Vercel / Netlify | Vercel CLI or GitHub Actions |
| 7 | Worker starts backend on Railway / Render | `railway up` or Render dashboard |
| 8 | Worker adds URLs to .env and generates deliverable-manifest.json | Edit files, `git add . && git commit -m "deliverable"` |
| 9 | Worker pushes repo → makes worker address a collaborator | `git remote add origin … && git push` |
| 10 | Worker adds repo URL, SPEC_HASH, DELIVERABLE_HASH to TaskEscrow | CLI or agent script |
| 11 | Verifier bot runs all acceptance-criteria checks | Playwright test suite + k6 + ZAP |
| 12 | Verifier uploads verification report to IPFS → VERIF_REPORT_HASH | `ipfs add report.json` |
| 13 | Verifier calls `ReceiptVerifier.verifyTask(taskId, true, VERIF_REPORT_HASH)` | Smart-contract call |
| 14 | Payment released → ERC-8004 receipt minted | On-chain transaction |
| 15 | If client disputes → trigger juror voting | `DisputeArbitration.disputeTask(taskId)` |
| 16 | After approval, repo is marked final; optionally archive it | GitHub "Release" or "Tag" |

## 7. Why This Is the Optimal Way for COVENANT

| Goal | How the above satisfies it |
|------|---------------------------|
| **Zero trust** | All checks are executed by an automated verifier bot; no human must manually inspect screenshots |
| **Fast & cheap** | Batch the verification of multiple criteria in a single transaction (verifyBatch). Heavy-weight checks (security scan, visual regression) are cached locally and reused |
| **Scalable 3-D workloads** | Use milestone-funding – the client can release part of the payment after the API is live, another part after visual checks pass, etc. |
| **Clear dispute path** | The on-chain DisputeArbitration contract already implements juror voting; you just plug the 3-D visual-regression evidence into it |
| **Human-centric fallback** | Jurors can subjectively vote "the colour looks wrong" or "the animation is choppy". The majority decision overrides the automated score if needed |
| **Future-proof** | The spec lives on IPFS forever; any change (even a tiny UI tweak) creates a new spec hash → a brand-new task, so you never have to rewrite old contracts |
| **Reuse of existing tools** | Playwright (already wired for visual regression), k6 (performance), OWASP ZAP (security), and the TaskEscrow contract are all part of the default COVENANT stack – no extra infrastructure required |

## 8. TL;DR – What You Must Do Next

1. **Write the spec JSON** (include visual-regression targets for your 3-D background)
2. **IPFS-pin it** and keep the hash
3. **Create the task** on TaskEscrow and fund it with the agreed ETH
4. **Worker builds** → tests → builds → deploys → adds repo URLs → pushes a manifest
5. **Submit the deliverableHash** to the contract
6. **Verifier runs** the full suite (URL, API, Playwright snapshots, coverage, security)
7. **If score ≥ 75** and all blocking checks pass → verification succeeds, payment is released
8. **If client dislikes result** → open a dispute, jurors re-verify, vote, and the outcome is enforced on-chain

---

## Conclusion

Follow the checklist above, and you'll be able to safely hand off any massive 3-D portfolio or blockchain-backed application to the COVENANT platform, know exactly how it will be inspected, and have a clear, provably fair path to fix it if the client isn't satisfied.

**Key Solution for Big Projects:**
- Finish and push all works to a GitHub repo
- Change collaborator access to include worker/verifier addresses
- Store only IPFS hashes on-chain (spec, deliverable manifest, verification report)
- Use automated verification with juror fallback for subjective disputes
